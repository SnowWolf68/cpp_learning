#### thread库

- thread库文档 https://zh.cppreference.com/w/cpp/thread/thread 和 https://legacy.cppplus.com/reference/thread/thread/  
- thread库底层是对各个系统的线程库进行封装，如Linux下的pthread库和Windows下Thread库等，所以C++11 thread库的第一个特点是可以跨平台，第二个特点是Linux和Windows下提供的线程库都是面向过程的，C++11 thread是库面向对象的，并且融合了一些C++11语言特点，如右值引用的移动语义，可变模板参数等，用起来会更好用一些。  
- 下面线程创建这里有4个构造函数，日常最常用的是第2个，他支持传一个可调用对象和参数即可，相比pthread_create而言，这里不再局限于只传递函数指针，其次就是参数传递也更方便，pthread_create调用时，要传递多个参数需要打包成一个结构体，传结构体对象的指针过去。

- join是主线程结束前需要阻塞等待创建的从线程，否则主线程结束，进程就结束了，从线程可能还在运行就被强行终止了。  
- class thread::id是一个thread的内部类用来表示线程id，支持比较大小，插入和提取，通过特化hash仿函数做unordered_map和unordered_set的id等。底层的角度看thread本质还是封装各个平台的线程库接口。各个平台的线程id表示类型不同，所以只能看一个类来进行封装。线程对象可以通过get_id获取线程id，在执行体内可以通过this_thread::get_id()获取线程id。

#### this_thread

- yield是主动让出当前线程的执行权，让其他线程先执行。此函数的确切行为依赖于实现，特别是取决于使用中的 OS 调度器机制和系统状态。例如，先进先出实时调度器（Linux 的 SCHED_FIFO）会挂起当前线程并将其放到准备运行的同优先级线程的队列尾，而若无其他线程在同优先级，则 yield 无效果。

####  mutex  
- https://legacy.cppreference.com/reference/mutex/  
- mutex是封装的互斥锁的类，用于保护临界区的共享数据。mutex主要提供lock和unlock两个接口函数。mutex 提供排他性非递归所有权语义：（1）调用方线程从它成功调用 lock或 try_lock 开始，到它调用 unlock 为止占有 mutex。（2）线程占有 mutex 时，其他线程如果试图要求 mutex 的所有权，那么就会阻塞（对于 lock 的调用），对于 try_lock就会返回false。  
- 如果 mutex 在仍为任何线程所占有时即被销毁，或在占有 mutex 时线程终止，那么行为未定义。  
- 示例1代码展示了mutex的使用，其实如果线程对象传参给可调用对象时，使用引用方式传参，实参位置需要加上ref(obj)的方式，主要原因thread本质还是系统库提供的线程库API的封装，thread 构造取到参数包以后，要调用创建线程的API，还是需要将参数包打包成一个结构体传参过去，那么打包成结构体时，参数包对象就会拷贝给结构体对象，使用ref传参的参数，会让结构体中的对应参数成员类型推导为引用，这样才能实现引用传参，示例2代码截取了vs2019下标准库中的部分源码帮助理解。https://legacy.cppreference.com/reference/functional/ref?kw=ref  
- time_mutex跟mutex完全类似，只是额外提供try_lock_for和try_lock_until的接口，这两个接口跟try_lock类似，只是他不会马上返回，而是直接进入阻塞，直到时间条件到了或者解锁了就会唤醒试图获取锁资源。  
- recursive_mutex 跟mutex完全类似，recursive_mutex 提供排他性递归所有权语义：（1）调用方线程在从它成功调用 lock 或 try_lock 开始的时期里占有 recursive_mutex。此时期之内，线程可以进行对 lock 或 try_lock 的附加调用。所有权的时期在线程进行匹配次数的 unlock 调用时结束。（2）线程占有 recursive_mutex 时，若其他所有线程试图要求 recursive_mutex 的所有权，则它们将阻塞（对于调用 lock）或收到 false 返回值（对于调用 try_lock）

```cc
#include <iostream>
#include <mutex>
#include <thread>
using namespace std;

void Print(int n, int &rx, mutex &rmtx) {
	rmtx.lock();

	for (int i = 0; i < n; i++) {
		// t1 t2
		++rx;
	}

	rmtx.unlock();
}
int main() {
	int x = 0;
	mutex mtx;
	// 这里必须要用ref()传参，线程中拿到的才是x和mtx的引用，具体原因需要看下面thread源码中的分析
	// https://legacy.cplusplus.com/reference/functional/ref/?kw=ref
	thread t1(Print, 1000000, ref(x), ref(mtx));
	thread t2(Print, 2000000, ref(x), ref(mtx));

	t1.join();
	t2.join();

	cout << x << endl;
    
	return 0;
}

int main() {
	int x = 0;
	mutex mtx;
    
	// 将上面的代码改成使用lambda捕获外层的对象，也就可以不用传参数，间接解决了上面的问题
	auto Print = [&x, &mtx](size_t n) {
		mtx.lock();
		for (size_t i = 0; i < n; i++) {
			++x;
		}
		mtx.unlock();
	};
    
	thread t1(Print, 1000000);
	thread t2(Print, 2000000);
    
	t1.join();
	t2.join();
    
	cout << x << endl;
    
	return 0;
```

```cc
		  enable_if_t<!is_same_v<_Remove_cvref_t<_Fn>, thread>, int> = 0>
_NODISCARD_CTOR explicit thread(_Fn &&_Fx, _Args &&..._Ax) {
	_Start(_STD forward<_Fn>(_Fx), _STD forward<_Args>(_Ax)...);
}

template <class _Fn, class... _Args>
void _Start(_Fn &&_Fx, _Args &&..._Ax) {
	// 从下面可以看到，线程要调用系统库的线程，最终还是要把参数包打包成一个结构体对象再传给线程，所以线程中拿到的参数包值是我们传的参数包值的拷贝，所以要用ref才传参才能解决问题
	using _Tuple = tuple<decay_t<_Fn>, decay_t<_Args>...>;
	auto _Decay_copied = _STD make_unique<_Tuple>(_STD forward<_Fn>(_Fx),
												  _STD forward<_Args>(_Ax)...);
	constexpr auto _Invoker_proc =
		_Get_invoke<_Tuple>(make_index_sequence<1 + sizeof...(_Args)>{});
        
	// pointer or reference to potentially throwing function passed to
	// extern C function under -EHc. Undefined behavior may occur
	// if this function throws an exception. (/Wall)
	_Thr._Hnd = reinterpret_cast<void *>(_CSTD _beginthreadex(
		nullptr, 0, _Invoker_proc, _Decay_copied.get(), 0, &_Thr._Id));
	if (_Thr._Hnd) { // ownership transferred to the thread
		(void)_Decay_copied.release();
	} else { // failed to start thread
		_Thr._Id = 0;
		_Throw_Cpp_error(_RESOURCE_UNAVAILABLE_TRY_AGAIN);
	}
}
```

#### lock_guard  
- lock_guard是C++11提供的支持RAII方式管理互斥锁资源的类，这样可以更有效的防止因为异常等原因导致的死锁问题。他们的大致原理如下面模拟提供的示例代码1的LockGuard类似。  
- lock_guard的功能简单纯粹，仅支持RAII的方式管理锁对象。也可以在构造的时候通过传参adopt_lock_t的adopt_lock对象管理已经lock的锁对象。其次lock_guard类不支持拷贝构造。

```cc
	~LockGuard() { _mtx.unlock(); }

private:
	Mutex &_mtx;
};
int main() {
	int x = 0;
	mutex mtx;
	auto Print = [&x, &mtx](size_t n) {
		// lock_guard<mutex> lock(mtx);
		LockGuard<mutex> lock(mtx);
		// mtx.lock();
		for (size_t i = 0; i < n; i++) {
			++x;
		}
		// mtx.unlock();
	};
	thread t1(Print, 1000000);
	thread t2(Print, 2000000);
	t1.join();
	t2.join();

	return 0;
```

#### unique_lock
- unique_lock也是C++11提供的支持RAII方式管理互斥锁资源的类，相比lock_guard他的功能支持更丰富复杂。这是unique_lock的https://legacy.cplusplus.com/reference/mutex/unique_lock/

  简单来说，`std::unique_lock` 比 `std::lock_guard` 更加灵活，但也因此带来了一点点额外的性能开销。

- unique_lock首先在构造的时候传不同的tag，用以支持在构造的时候不同的方式处理锁对象

  ![image-20260219100638335](E:\cpp_linux_learning\C++\learning\cpp_learning\notes\img_C++11并发支持库\image-20260219100638335.png)
- unique_lock首先在构造的时候传时间段和时间点，用来管理time_mutex系统，构造时调用try_lock_for和try_lock_until
- unique_lock不支持拷贝和赋值，支持移动构造和移动赋值。
- unique_lock还提供了lock/try_lock/unlock等系列的接口等系统的接口。
- unique_lock还可以通过operator bool检查是否locked了锁对象。

1. 常用构造方式（锁策略 tag）

   1) 默认：构造即加锁

   ```cpp
   std::unique_lock<std::mutex> lk(m);
   ```

   2) 延迟加锁：`std::defer_lock`

   ```cpp
   std::unique_lock<std::mutex> lk(m, std::defer_lock); // 此时不持锁
   lk.lock();
   ```

   3) 尝试加锁：`std::try_to_lock`

   ```cpp
   std::unique_lock<std::mutex> lk(m, std::try_to_lock);
   if (!lk.owns_lock()) { /* 没拿到锁 */ }
   ```

   4) 接管锁：`std::adopt_lock`

   ```cpp
   m.lock();
   std::unique_lock<std::mutex> lk(m, std::adopt_lock); // lk 接管，析构时会解锁
   ```

2. 常用成员函数（最常见的一批）

   1) 加锁/解锁

   - `void lock();`（阻塞直到拿到锁）
   - `bool try_lock();`（不阻塞）
   - `void unlock();`（释放锁）

   示例：临时释放锁

   ```cpp
   std::unique_lock<std::mutex> lk(m);
   // 临界区...
   lk.unlock();   // 暂时放开
   // 非临界区...
   lk.lock();     // 再次进入临界区
   ```

   2) 是否持有锁

   - `bool owns_lock() const noexcept;`

   ```cpp
   std::unique_lock<std::mutex> lk(m, std::try_to_lock);
   if (lk.owns_lock()) { /* ... */ }
   ```

   3) 访问/交换底层互斥量

   - `mutex_type* mutex() const noexcept;`（返回指向 mutex 的指针，可能为 `nullptr`）
   - `void swap(unique_lock& other) noexcept;` 或 `std::swap(lk1, lk2);`

   4) 释放管理权（危险但有用）

   - `mutex_type* release() noexcept;`  
     作用：让 `unique_lock` 不再负责这个 mutex（**不会解锁**），返回 mutex 指针，后续你得自己处理解锁/生命周期。

   ```cpp
   std::unique_lock<std::mutex> lk(m);
   // ...
   std::mutex* pm = lk.release(); // lk 变成“空的”，且 m 仍然保持加锁状态
   pm->unlock();                  // 需要你自己解锁
   ```

   5) 其他常用查询

   - `explicit operator bool() const noexcept;`（等价于 `owns_lock()`，常用于 `if(lk)`）
   - `unique_lock(unique_lock&&);` / `operator=(unique_lock&&);`（可移动）

#### condition_variable

- condition_variable需要配合互斥锁系列进行使用，主要提供wait和notify系统接口。
- wait需要传递一个unique_lock<mutex>类型的互斥锁，wait会阻塞当前线程直到被notify。在进入阻塞的一瞬间，会解开互斥锁，方便其他线程获取锁，访问条件变量。当被notify唤醒时，他会同时获取到锁，再继续往下运行。
- notify_one会唤醒当前条件变量上等待的其中一个线程，使用时他也需要用互斥锁保护，如果没有现成阻塞等待，他啥事都不做；notify_all会唤醒当前条件变量上等待的所有线程进程。
- condition_variable_any类是std::condition_variable的泛化。相对于只在`std::unique_lock<std::mutex>` 上工作的`std::condition_variable`，`condition_variable_any` 能在任何满足可基本锁定（BasicLockable）要求的锁上工作。

```cc
// condition_variable::notify_all
#include <condition_variable> // std::condition_variable
#include <iostream>			  // std::cout
#include <mutex>			  // std::mutex, std::unique_lock
#include <thread>			  // std::thread

std::mutex mtx;
std::condition_variable cv;

bool ready = false;

void print_id(int id) {
	std::unique_lock<std::mutex> lck(mtx);
	while (!ready)
		cv.wait(lck);
	// ...
	std::cout << "thread " << id << '\n';
}

void go() {
	std::unique_lock<std::mutex> lck(mtx);
	ready = true;

	// 通知所有阻塞在条件变量上的线程
	cv.notify_all();
}

int main() {
	std::thread threads[10];

	// spawn 10 threads:
	for (int i = 0; i < 10; ++i)
		threads[i] = std::thread(print_id, i);

	std::cout << "10 threads ready to race...\n";
	std::this_thread::sleep_for(std::chrono::milliseconds(100));

	go(); // go!
	
    for (auto &th : threads)
		th.join();
    
	return 0;
}
```

> - 情况1：t1先启动，t2过了一会才启动(未启动或者还在排队)
>
>   - t1启动以后先获取锁，flag是true不会被条件变量阻塞，打印i为0，flag修改为false，i修改为2，再用条件变量唤醒其他阻塞线程，但是没有线程等待，循环再继续，再次获取锁，flag刚修改为false了，这时会阻塞在条件变量上，并且解锁，这里的逻辑保证了t1不会连续打印。
>   - t2这时开始运行，先获取锁，flag被t1修改为false了所以t2不会被条件变量阻塞，t1打印i为1，flag修改为true，j修改为3，再用条件变量唤醒其他阻塞线程，t1被唤醒。那么这里t1被唤醒以后，也是需要分配时间片排队执行，这时有2种情况，第一种t1没有立即执行，t2继续执行，t2获取锁，但是flag为true，所以阻塞在条件变量并且解锁，过一会t1开始执行了，flag为true不会被条件变量继续阻塞，打印2，继续上述循环逻辑，就交替打印了。第二种t1立即执行，t1抢占到锁，flag为true不会被条件变量继续阻塞，打印2，i修改为4，flag修改为false，再用条件变量唤醒其他阻塞线程，但是没有线程被阻塞，再继续循环逻辑就是t1和t2新一轮谁先执行或者抢到锁资源的逻辑了，这样也实现了交替打印。
>
> - 情况2：t2先启动，t1过了一会才启动(未启动或者还在排队)
>
>   - t2启动以后先获取锁，flag是true会被条件变量阻塞，并且同时解锁。
>   - 一会后，t1开始运行，获取到锁资源，flag是true不会被条件变量阻塞，打印i为0，flag修改为false，i修改为2，再用条件变量唤醒阻塞线程t2。跟上面类似，t2被唤醒以后也是需要分配时间片排队执行，这时有2种情况，第一种t2没有立即执行，t1继续执行循环，获取锁，但是flag为false，所以阻塞在条件变量并且解锁。过一会t2开始执行了，flag为false不会被条件变量继续阻塞，打印1，j修改为3，flag修改为true，唤醒阻塞线程t1，这时跟上述逻辑类似，循环往复，就可以实现交替打印了。第二种t2立即执行，t2抢到锁，flag为false不会被条件变量继续阻塞，打印1，j修改为3，flag修改为true，唤醒其他阻塞线程，这没有线程被其他条件变量阻塞，再继续循环逻辑就是t1和t2新一轮谁先执行或者抢到锁资源的逻辑了，这样也实现了交替打印。
>
> - 情况3：t1和t2几乎同时启动
>
>   - 这种情况，本质就是两个线程抢夺先锁资源，t1先抢到就类似情况1，t2先抢到就类似情况2，这里就不再细节分析了。

```cc
// 下面演示一个经典问题，两个线程交替打印奇数和偶数
#include <condition_variable> // std::condition_variable
#include <iostream>			  // std::cout
#include <mutex>			  // std::mutex, std::unique_lock
#include <thread>			  // std::thread
using namespace std;
int main() {
	std::mutex mtx;
	condition_variable c;
	int n = 100;
	bool flag = true;
	// 第一个打印的是t1打印0
	thread t1([&]() {
		int i = 0;
		while (i < n) {
			unique_lock<mutex> lock(mtx);
			// flag == false t1一直阻塞
			// flag == true t1不会阻塞
			while (!flag) {
				c.wait(lock);
			}
			cout << i << endl;
			flag = false;
			i += 2; // 偶数
			c.notify_one();
		}
	});
	// this_thread::sleep_for(std::chrono::milliseconds(3000));
	thread t2([&]() {
		int j = 1;
		while (j < n) {
			unique_lock<mutex> lock(mtx);
			// 只要flag == true t2一直阻塞
			// 只要flag == false t2不会阻塞
			while (flag)
				c.wait(lock);
			cout << j << endl;
			j += 2; // 奇数
			flag = true;
			c.notify_one();
		}
	});
	t1.join();
	t2.join();
	return 0;
}
```

##### condition_variable接口总结

###### 1. 前置条件

使用 `condition_variable` 必须配合 **`std::mutex`** 和 **`std::unique_lock`** 一起使用。
*   为什么是 `unique_lock` 而不是 `lock_guard`？
    因为 `wait()` 方法在进入休眠前需要解锁互斥量，被唤醒后需要重新加锁。只有 `unique_lock` 提供了这种灵活的锁管理机制。
    
    > 要理解为什么非用 `unique_lock` 不可，我们需要深入到 `condition_variable::wait()` 的**内部工作原理**，以及 `lock_guard` 和 `unique_lock` 的**设计区别**中去。
    >
    > ###### 1. 核心矛盾：`wait()` 的“三步走”动作
    >
    > 当你在线程 A 中调用 `cv.wait(lock)` 时，这个函数并不是简单地让线程睡觉。为了避免死锁，它必须在后台原子地完成以下三个步骤：
    >
    > 1.  **解锁（Unlock）**：线程 A **必须释放**它持有的互斥锁。
    >     *   *为什么？* 因为如果不释放锁，线程 A 抱着锁睡着了，其他线程（线程 B）就永远拿不到锁，也就无法修改共享变量（比如往队列里放数据），更无法通知线程 A。这就造成了**死锁**。
    > 2.  **休眠（Sleep）**：线程 A 进入等待状态，此时它不再持有锁。
    > 3.  **加锁（Relock）**：当线程 A 被 `notify` 唤醒（或者超时、虚假唤醒）准备继续执行时，它必须**重新抢回**互斥锁。
    >     *   *为什么？* 因为 `wait` 返回后，线程 A 通常需要再次检查共享变量（比如 `while(!condition)`），访问共享变量必须持有锁。
    >
    > ###### 2. `lock_guard` vs `unique_lock` 的能力差异
    >
    > 为了完成上述“解锁 -> 休眠 -> 加锁”的动作，传入 `wait()` 的锁管理对象必须具备**随时手动解锁和加锁**的能力。
    >
    > A. `std::lock_guard`：死板的守卫
    > *   **设计理念**：极简主义，RAII（资源获取即初始化）。
    > *   **生命周期**：构造时加锁，析构时解锁。
    > *   **致命缺陷**：**它没有提供 `.lock()` 和 `.unlock()` 成员函数！**
    >     *   一旦你创建了 `lock_guard`，在这个对象销毁之前，你**无法**临时释放锁。
    >     *   这就好比你把钥匙用强力胶粘在手上了，你想睡觉（wait），但你没法把钥匙交给别人（释放锁），所以别人进不来，你也醒不了。
    >
    > B. `std::unique_lock`：灵活的管家
    > *   **设计理念**：功能丰富，同样是 RAII，但支持手动控制。
    > *   **能力**：
    >     *   它内部有一个 `owns_lock` 标志位，记录当前是否持有锁。
    >     *   **它提供了 `.lock()` 和 `.unlock()` 公开成员函数。**
    >     *   它允许在对象生命周期内多次加锁、解锁。
    >     *   它甚至可以“延迟加锁”（`std::defer_lock`）。
    >
    > ###### 3. 为什么 `wait` 需要 `unique_lock`？（源码视角）
    >
    > 假设我们看一眼 `cv.wait(lock)` 的伪代码实现，它大致长这样：
    >
    > ```cpp
    > // 伪代码：condition_variable::wait 内部逻辑
    > void wait(std::unique_lock<std::mutex>& lock) {
    >     // 1. 调用 lock 对象的 unlock() 方法释放锁
    >     // 如果传进来的是 lock_guard，这里直接编译报错，因为它没有 unlock() 方法！
    >     lock.unlock(); 
    >     
    >     // 2. 将当前线程加入等待队列，进入内核态休眠
    >     // ... magic happens here ...
    >     
    >     // 3. 线程被唤醒后，在返回之前，必须重新拿锁
    >     // 如果是 lock_guard，这里也报错，因为它没有 lock() 方法！
    >     lock.lock();
    > }
    > ```
    >
    > 正是因为 `wait` 函数内部**显式调用**了传入对象的 `.unlock()` 和 `.lock()` 方法，所以 C++ 标准库强制要求参数类型必须是 `std::unique_lock`。

###### 2. 等待接口 (Waiting)

等待接口由消费者（等待者）调用。

1. `wait()` - 无限等待

  这是最常用的函数。它有两种形式：

  **形式 1**：无谓词版本（不推荐单独使用）

  ```cpp
  cv.wait(lock);
  ```

  *   行为：
      1.  原子地释放 `lock` 锁。
      2.  阻塞当前线程，进入等待状态。
      3.  当被 `notify` 唤醒时，重新获取 `lock` 锁，然后函数返回。
  *   缺点：容易受到 “虚假唤醒”（Spurious Wakeup） 的影响（即没有收到 notify 信号，线程却莫名其妙醒了）。

  **形式 2**：带谓词版本（推荐！）

  ```cpp
  // pred 是一个返回 bool 的函数或 Lambda 表达式
  cv.wait(lock, []{ return ready; }); 
  ```

  *   行为：等价于 `while (!pred()) { cv.wait(lock); }`。
  *   逻辑：
      1.  先检查 `pred()` 是否为真。如果是真，直接继续执行（不睡）。
      2.  如果是假，才释放锁并睡觉。
      3.  醒来后，再次检查 `pred()`。如果还是假（说明是虚假唤醒），继续睡。
  *   优点：完美解决了虚假唤醒问题。

2. `wait_for()` - 等待一段时间

   ```cpp
   // 等待 100 毫秒
   if (cv.wait_for(lock, std::chrono::milliseconds(100)) == std::cv_status::timeout) {
       // 超时了还没醒，或者醒了条件不满足
   }
   ```

   *   用于设置超时时间。如果在指定时间内没收到通知，函数会自动返回。
   *   同样支持带谓词的版本：`cv.wait_for(lock, time, pred)`。
3. `wait_until()` - 等待到某个时间点

   ```cpp
   // 等待直到明天早上 8 点
   cv.wait_until(lock, sys_time_point);
   ```

   *   与 `wait_for` 类似，只是参数从“时长”变成了“具体的截止时间点”。
---

###### 3. 通知接口 (Notifying)

通知接口由生产者（改变条件的人）调用。调用通知时不需要持有锁（虽然持有锁也可以，但为了性能通常建议解锁后再通知）。

1. `notify_one()` - 唤醒一个

   ```cpp
   cv.notify_one();
   ```
   *   行为：随机唤醒一个正在等待该条件变量的线程。
   *   场景：适用于“独占性”任务。例如队列里进了一个任务，只需要唤醒一个消费者去处理，唤醒多了也是浪费（惊群效应）。


2. `notify_all()` - 唤醒所有

   ```cpp
   cv.notify_all();
   ```

   *   行为：唤醒所有正在等待该条件变量的线程。
   *   场景：
       1.  广播事件：例如“程序要退出了”，通知所有工作线程停止手头工作。
       2.  共享资源：例如“数据加载完毕”，所有读取线程都可以开始读了。
