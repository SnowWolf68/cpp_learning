### 智能指针的使用场景

下面程序中我们可以看到，new了以后，我们也delete了，但是因为抛异常导，后面的delete没有得到执行，所以就内存泄漏了，所以我们需要new以后捕获异常，捕获到异常后delete内存，再把异常抛出，但是因为new本身也可能抛异常，连续的两个new和下面的Divide都可能会抛异常，让我们处理起来很麻烦。智能指针放到这样的场景里面就让问题简单多了。

```cc
#include<iostream>
using namespace std;

double Divide(int a, int b) {
	// 当b == 0时抛出异常
	if (b == 0) {
		throw "Divide by zero condition!";
	} else {
		return (double)a / (double)b;
	}
}
void Func() {
	// 这里可以看到如果发生除0错误抛出异常，另外下面的array和array2没有得到释放。
	// 所以这里捕获异常后并不处理异常，异常还是交给外面处理，这里捕获了再重新抛出去。
	// 但是如果array2new的时候抛异常呢，就还需要套一层捕获释放逻辑，这里更好解决方案
	// 是智能指针，否则代码太戳了
	int *array1 = new int[10];
	int *array2 = new int[10]; // 抛异常呢
	int len = 1, time = 0;
    cout << Divide(len, time) << endl;
	// ...
	cout << "delete []" << array1 << endl;
	delete[] array1;
	cout << "delete []" << array2 << endl;
	delete[] array2;
}
int main() {
	try {
		Func();
	} catch (const char *errmsg) {
		cout << errmsg << endl;
	} catch (const exception &e) {
		cout << e.what() << endl;
	} catch (...) {
		cout << "未知异常" << endl;
	}
	return 0;
}
```

### RAII和智能指针的设计思路

- RAlI是Resource Acquisition Is Initialization的缩写，他是一种管理资源的类的设计思想，本质是一种利用对象生命周期来管理获取到的动态资源，避免资源泄漏，这里的资源可以是内存、文件指针、网络连接、互斥锁等等。RAII在获取资源时把资源委托给一个对象，接着控制对资源的访问，资源在对象的生命周期内始终保持有效，最后在对象析构的时候释放资源，这样保障了资源的正常释放，避免资源泄漏问题。

- 智能指针类除了满足RAII的设计思路，还要方便资源的访问，所以智能指针类还会像迭代器类一样，重载 `operator*/operator->/operator[]` 等运算符，方便访问资源。

```cc
// SmartPtr.hpp
namespace snow {
	template <class T>
	class SmartPtr {
	public:
		SmartPtr(T* ptr) : _ptr(ptr) {}
		~SmartPtr() { delete[] _ptr; }
		T operator*() { return *_ptr; }
		T operator->() { return _ptr; }
		T& operator[](int i) { return _ptr[i]; }

	private:
		T* _ptr;
	};
} // namespace snow
```

### C++标准库智能指针的使用

- C++标准库中的智能指针都在`<memory>`这个头文件下面，我们包含`<memory>`就可以是使用了，智能指针有好几种，除了`weak_ptr`他们都符合RAII和像指针一样访问的行为，原理上而言主要是解决智能指针拷贝时的思路不同。
- `auto_ptr`是C++98时设计出来的智能指针，他的特点是拷贝时把被拷贝对象的资源的管理权转移给拷贝对象，这是一个非常糟糕的设计，因为他会被拷贝对象悬空，访问报错的问题，C++11设计出新的智能指针后，强烈建议不要使用`auto_ptr`。其他C++11出来之前很多公司也是明令禁止使用这个智能指针的。
- `unique_ptr`是C++11设计出来的智能指针，他的名字翻译出来是唯一指针，他的特点的不支持拷贝，只支持移动。如果不需要拷贝的场景就非常建议使用他。
- `shared_ptr`是C++11设计出来的智能指针，他的名字翻译出来是共享指针，他的特点是支持拷贝，也支持移动。如果需要拷贝的场景就需要使用他了。底层是用引用计数的方式实现的。
- `weak_ptr`是C++11设计出来的智能指针，他的名字翻译出来是弱指针，他完全不同于上面的智能指针，他不支持RAII，也就意味着不能用它直接管理资源，`weak_ptr`的产生本质是要解决`shared_ptr`的一个循环引用导致内存泄漏的问题。具体细节下面我们再细讲。
- 智能指针析构时默认是进行delete释放资源，这也就意味着如果不是new出来的资源，交给智能指针管理，析构时就会崩溃。智能指针支持在构造时给一个删除器，所谓删除器本质就是一个可调用对象，这个可调用对象中实现你想要的释放资源的方式，当构造智能指针时，给了定制的删除器，在智能指针析构时就会调用删除器去释放资源。因为`new[]`经常使用，所以为了简洁一点，`unique_ptr`和`shared_ptr`都特化了一份`[]`的版本，使用时`unique_ptr<Date[]> up1(new Date[5]);` `shared_ptr<Date[]> sp1(new Date[5]);`就可以管理`new[]`的资源。
- `template <class T, class... Args> shared_ptr<T> make_shared (Args&&... args);`
- `shared_ptr`除了支持用指向资源的指针构造，还支持`make_shared`用初始化资源对象的值直接构造。
- `shared_ptr`和`unique_ptr`都支持了`operator bool`的类型转换，如果智能指针对象是一个空对象没有管理资源，则返回`false`，否则返回`true`，意味着我们可以直接把智能指针对象给if判断是否为空。
- `shared_ptr`和`unique_ptr`都得构造函数都使用`explicit`修饰，防止普通指针隐式类型转换成智能指针对象。

#### C++标准库智能指针的基本特性

```cc

	int _month;
	int _day;

	auto_ptr<Date> ap1(new Date);
	// 拷贝时，管理权限转移，被拷贝对象ap1悬空

	// 空指针访问，ap1对象已经悬空
	// ap1->_year++;
    
	unique_ptr<Date> up1(new Date);
	// 不支持拷贝
	// unique_ptr<Date> up2(up1);
    
	// 支持移动，但是移动后up1也悬空，所以使用移动要谨慎
	unique_ptr<Date> up3(move(up1));

	// 支持拷贝

	cout << sp1->_year << endl;         // 2
	cout << sp2->_year << endl;         // 2
	cout << sp3->_year << endl;         // 2
```

为什么要有删除器

```cc
unique_ptr<Date> up1(new Date[10]);
shared_ptr<Date> sp1(new Date[10]);
```

这样会崩溃

```shell

munmap_chunk(): invalid pointer
```

> 因为: 
>
> 会崩溃的根本原因是：你用 **`new Date[10]` 分配的是数组**，但
>
> - `unique_ptr<Date>` 的默认删除器是 `delete ptr;`（删除单个对象）
> - `shared_ptr<Date>` 的默认删除器也是 `delete ptr;`
>
> 也就是说析构时会对数组首元素指针执行 **`delete` 而不是 `delete[]`**，这是 **未定义行为（UB）**：可能只析构一个元素、破坏堆结构、直接崩溃。

+ 解决方案1: 

  ```cc
  // 解决方案1
  // 因为new[]经常使用，所以unique_ptr和shared_ptr
  // 实现了一个特化版本，这个特化版本析构时用的delete[]
  unique_ptr<Date[]> up1(new Date[5]);
  shared_ptr<Date[]> sp1(new Date[5]);
  ```

+ 解决方案2: 自定义删除器

> `deltype`:
>
> + 关键字decltype将变量的类型声明为表达式指定的类型。
>
> ```cc
> // decltype的一些使用使用场景
> template <class T1, class T2>
> void F(T1 t1, T2 t2) {
> 	decltype(t1 * t2) ret;
> 	cout << typeid(ret).name() << endl;
> }
> int main() {
> 	const int x = 1;
> 	double y = 2.2;
>     
> 	decltype(x * y) ret; // ret的类型是double
> 	decltype(&x) p;		 // p的类型是int*
> 	cout << typeid(ret).name() << endl;
> 	cout << typeid(p).name() << endl;
>     
> 	F(1, 'a');
>     
> 	return 0;
> }
> ```
>
> > `decltype` 是 C++11 引入的关键字，用于**在编译期从一个表达式推导出“精确类型”**（包括 `const`/引用等修饰）。它常用于泛型编程、返回类型推导、写出“与某表达式同类型”的变量等。
> >
> > 下面按“作用—规则—例子—典型用法”来单独介绍。
> >
> > ---
> >
> > ##### 1）`decltype` 的作用是什么
> >
> > - **获取表达式的类型**：`decltype(expr)` 得到 `expr` 的类型（但不会对 `expr` 求值）
> > - 类型推导更“精确”：相比 `auto`，`decltype` 更倾向于**保留引用与 cv 限定**（const/volatile）
> > - 常用于：
> >   - 写出依赖模板参数的返回类型（尤其 C++11/14）
> >   - “跟随表达式类型”声明变量
> >   - `decltype(auto)` 做“按表达式原样返回”（保留引用）
> >
> > ---
> >
> > ##### 2）核心语法
> >
> > ```cpp
> > decltype(表达式) 变量名;
> > ```
> >
> > 例如：
> > ```cpp
> > int x = 0;
> > decltype(x) y = x;   // y 的类型是 int
> > ```
> >
> > 注意：`decltype` 只做类型推导，不会运行表达式。
> >
> > ---
> >
> > ##### 3）`decltype` 的推导规则（最重要）
> >
> > `decltype(e)` 的结果取决于 `e` 的形式与值类别（lvalue/xvalue/prvalue）。规则可以记成两段：
> >
> > ###### 规则 A：特殊情况（最常用也最容易忽略）
> > 如果 `e` 是**不带括号的**变量名（id-expression）或类成员访问（member access），则：
> >
> > - `decltype(e)` 得到的是该实体的**声明类型**（原封不动，含 const、引用等）
> >
> > 例子：
> > ```cpp
> > int x = 0;
> > int& rx = x;
> > const int cx = 1;
> > 
> > decltype(x)  a = 0;   // int
> > decltype(rx) b = x;   // int&   （保留引用！）
> > decltype(cx) c = 2;   // const int
> > ```
> >
> > ###### 规则 B：一般情况（看值类别）
> > 否则（更一般的表达式），按值类别：
> >
> > - 如果 `e` 是 **lvalue**，则 `decltype(e)` 是 `T&`
> > - 如果 `e` 是 **xvalue**，则 `decltype(e)` 是 `T&&`
> > - 如果 `e` 是 **prvalue**，则 `decltype(e)` 是 `T`
> >
> > 例子：
> > ```cpp
> > int x = 0;
> > 
> > decltype((x)) d = x;  // (x) 是 lvalue 表达式 => int&
> > decltype(x + 1) e = 0;// x+1 是 prvalue => int
> > ```
> >
> > ---
> >
> > ##### 4）最常见陷阱：`decltype(x)` vs `decltype((x))`
> >
> > ```cpp
> > int x = 0;
> > 
> > decltype(x)   a = x;  // int
> > decltype((x)) b = x;  // int&   （因为 (x) 是一个 lvalue 表达式）
> > ```
> >
> > - `x`（不带括号的变量名）触发“规则 A”：拿声明类型 `int`
> > - `(x)` 变成一般表达式，触发“规则 B”：lvalue => `int&`
> >
> > 这个差异在泛型返回类型、转发时非常关键。
> >
> > ---
> >
> > ##### 5）与 `auto` 的区别（怎么选）
> >
> > - `auto`：更像“按初始化推导一个值类型”，**通常会丢掉引用**（除非你写 `auto&` / `auto&&`）
> > - `decltype`：按表达式规则推导，**常会保留引用与 const**
> >
> > 例子：
> > ```cpp
> > int x = 0;
> > int& rx = x;
> > 
> > auto  a = rx;        // int    （引用被丢掉）
> > decltype(rx) b = x;  // int&   （保留引用）
> > ```
> >
> > ---
> >
> > ##### 6）`decltype(auto)`（C++14）——“完全按表达式返回/声明”
> >
> > `decltype(auto)` 让编译器用 `decltype(表达式)` 的规则来推导类型，常用于函数返回值：
> >
> > ```cpp
> > int x = 0;
> > int& get() { return x; }
> > 
> > decltype(auto) r1 = get(); // r1 是 int&
> > 
> > auto r2 = get();           // r2 是 int（拷贝）
> > ```
> >
> > ---
> >
> > ##### 7）典型用法汇总
> >
> > ###### 7.1 声明与某个表达式同类型的变量
> > ```cpp
> > template<class T, class U>
> > void f(T t, U u) {
> >     decltype(t + u) sum = t + u; // sum 的类型随 t+u 变化
> > }
> > ```
> >
> > ###### 7.2 用于“尾置返回类型”（C++11 常见）
> > 当返回类型依赖参数时：
> > ```cpp
> > template<class T, class U>
> > auto add(T a, U b) -> decltype(a + b) {
> >     return a + b;
> > }
> > ```
> >
> > ###### 7.3 配合完美转发（避免类型写错）
> > ```cpp
> > template<class F, class... Args>
> > decltype(auto) call(F&& f, Args&&... args) {
> >     return std::forward<F>(f)(std::forward<Args>(args)...);
> > }
> > ```
> >
> > ---

> `make_shared`
>
> > `std::make_shared` 是 C++11 提供的工厂函数，用来**创建对象并返回 `std::shared_ptr<T>`**。它的主要作用是：**更安全、更高效地创建 `shared_ptr`**，避免显式写 `new`，并且通常能减少一次动态内存分配。
> >
> > ---
> >
> > ##### 1）基本用法
> >
> > ###### 1.1 创建单个对象
> > ```cpp
> > #include <memory>
> > #include <string>
> > 
> > auto sp1 = std::make_shared<int>(42);
> > auto sp2 = std::make_shared<std::string>("hello");
> > ```
> >
> > 等价于“概念上”：
> > ```cpp
> > std::shared_ptr<int> sp(new int(42));
> > ```
> > 但 `make_shared` 通常更推荐。
> >
> > ###### 1.2 传构造参数（完美转发）
> > ```cpp
> > struct A {
> >  A(int x, std::string s) : x(x), s(std::move(s)) {}
> >  int x;
> >  std::string s;
> > };
> > 
> > auto sp = std::make_shared<A>(10, "abc");
> > ```
> >
> > ###### 1.3 默认构造
> > ```cpp
> > auto sp = std::make_shared<A>();
> > ```
> >
> > ---
> >
> > ##### 2）`make_shared` 的作用/优点
> >
> > ###### 2.1 异常安全：避免“new + shared_ptr”潜在泄漏窗口
> > 写法：
> > ```cpp
> > foo(std::shared_ptr<T>(new T), other()); 
> > ```
> > 如果在构造 `shared_ptr` 之前/过程中 `other()` 抛异常，某些复杂表达式里可能出现资源管理不够自然的情况。`make_shared` 把创建过程打包，写法更不易出错：
> >
> > ```cpp
> > foo(std::make_shared<T>(), other());
> > ```
> >
> > （更直观：减少显式 `new`，更符合 RAII）
> >
> > ###### 2.2 性能更好：常见实现只分配一次内存
> > 通常 `shared_ptr(new T)` 需要两块分配：
> > 1) `T` 对象本身一块  
> > 2) 控制块（引用计数、删除器等）一块
> >
> > 而 `make_shared<T>` 往往把“对象 + 控制块”放在同一块内存里：**一次分配**，更快、内存碎片更少、缓存局部性更好。
> >
> > ---
> >
> > ##### 3）限制与注意事项（很重要）
> >
> > ###### 3.1 不能直接指定自定义删除器
> > `make_shared<T>(...)` 只能按“默认删除策略”管理对象（最终用 `delete`）。如果你需要自定义删除器（比如 `fclose/free/delete[]/CloseHandle`），就不能用 `make_shared`：
> >
> > ```cpp
> > auto sp = std::shared_ptr<FILE>(
> >     fopen("a.txt","r"),
> >     [](FILE* f){ if(f) fclose(f); }
> > );
> > ```
> >
> > ###### 3.2 对象内存释放时机：可能比你想的更“晚”
> > 因为对象和控制块可能在同一块内存里：
> >
> > - 当最后一个 `shared_ptr` 销毁时：对象析构会发生
> > - 但如果还有 `weak_ptr` 存在：控制块仍在，整块内存可能要等到 `weak_ptr` 也都没了才真正释放
> >
> > 这点在“对象占用很大内存、但希望尽快归还内存”的场景要注意。  
> > （对象析构会执行，但那块大内存未必立刻释放回堆。）
> >
> > ###### 3.3 不适用于动态数组（C++ 标准库直到 C++20/23 才逐步完善相关支持）
> > 通常 `make_shared<T>` 面向单对象。动态数组用 `shared_ptr<T>` 管理也不太推荐；如果需要数组：
> > - 更推荐 `std::vector<T>` 或 `std::unique_ptr<T[]>`
> > - 或自己提供删除器：`shared_ptr<T>(new T[n], std::default_delete<T[]>())`（但仍需谨慎）
> >
> > ---
> >
> > ##### 4）与 `shared_ptr(new T(...))` 的选择建议
> >
> > 优先用：
> > ```cpp
> > auto sp = std::make_shared<T>(args...);
> > ```
> >
> > 除非你需要：
> > - 自定义删除器
> > - 自定义内存分配策略（`allocate_shared`）
> > - 或者明确希望对象与控制块分开分配（少数场景，如极大对象且 weak_ptr 生命周期很长）
> >
> > ---
> >
> > ##### 5）补充：`allocate_shared`（同类但更强）
> > 如果你需要使用自定义 allocator：
> > ```cpp
> > auto sp = std::allocate_shared<T>(alloc, args...);
> > ```
> > 它与 `make_shared` 类似，也通常一次分配，但能控制分配器。
> >
> > ---

> ##### 1）`shared_ptr` 的几种创建方式：`new` vs `make_shared`

> shared_ptr<Date> sp1(new Date(2024, 9, 11));
> shared_ptr<Date> sp2 = make_shared<Date>(2024, 9, 11);
> auto sp3 = make_shared<Date>(2024, 9, 11);
> ```

>   - 通常更高效：控制块和对象可能一次分配
>   - 更安全、更简洁：避免显式 `new`（更少出错点）
> - `auto sp3`：强调 `auto` 可以推导出 `std::shared_ptr<Date>`，写法更简洁。
>
> ---

> ```cpp
> shared_ptr<Date> sp4;

> - 默认构造后处于“空”状态：`sp4.get() == nullptr`，`use_count()==0`。
>
> ---

>
> ```cpp
> if (sp1) ...
> if (!sp4) ...
> ```
>
> - `shared_ptr` 提供了到 `bool` 的转换（`operator bool`），用于判断是否持有对象：
>   - `if (sp1)`：表示 `sp1` 非空
>   - `if (!sp4)`：表示 `sp4` 为空
> - 你注释里写的 `sp1.operator bool()` 说明你知道本质上是调用这个转换运算符。

>

> ##### 4）为什么这两句会“报错”：**构造函数是 `explicit`，拷贝初始化不允许隐式转换**
>
> ```cpp
> shared_ptr<Date> sp5 = new Date(2024, 9, 11);  // 报错
> unique_ptr<Date> sp6 = new Date(2024, 9, 11);  // 报错
> ```
>
> 这里的关键点是：`shared_ptr` / `unique_ptr` 从裸指针构造的构造函数是 `explicit` 的。
>
> - `T x = expr;` 这种形式叫 **拷贝初始化（copy-initialization）**  
>   它要求 `expr` 能**隐式转换**成 `T`。
> - 但 `explicit` 构造函数 **禁止隐式转换**，所以会报错。
>
> 正确写法应使用 **直接初始化（direct-initialization）** 或工厂函数：
>
> ```cpp
> shared_ptr<Date> sp5(new Date(2024, 9, 11));     // 直接初始化：OK
> auto sp5b = make_shared<Date>(2024, 9, 11);      // 更推荐
> 
> unique_ptr<Date> sp6(new Date(2024, 9, 11));     // 直接初始化：OK
> auto sp6b = make_unique<Date>(2024, 9, 11);      // 更推荐
> ```
>

### 智能指针的原理

- 下面我们模拟实现了auto_ptr和unique_ptr的核心功能，这两个智能指针的实现比较简单，大家了解一下原理即可。auto_ptr的思路是拷贝时转移资源管理权给被拷贝对象，这种思路是不被认可的，也不建议使用。unique_ptr的思路是不支持拷贝。
- 大家重点要看看shared_ptr是如何设计的，尤其是引用计数的设计，主要这里一份资源就需要一个引用计数，所以引用计数才用静态成员的方式是无法实现的，要使用堆上动态开辟的方式，构造智能指针对象时来一份资源，就要new一个引用计数出来。多个shared_ptr指向资源时就++引用计数，shared_ptr对象析构时就--引用计数，引用计数减到0时代表当前析构的shared_ptr是最后一个管理资源的对象，则析构资源。

> 几个问题
>
> 1. `shared_ptr`的引用计数为什么不能直接存储在成员位置, 而是要保存一份指向堆区的指针
>
>    ```cc
>    T* _ptr;
>    int* _p_count;
>    // int _p_count;	// 错误
>    ```
>
>    原因: **引用计数必须是“所有共享者共同维护的一份状态”**；而把它做成成员变量会导致**每个 shared_ptr 拷贝一份自己的计数**，计数根本共享不起来。

#### `auto_ptr`模拟实现

```cc
template <class T>
class auto_ptr {
public:
	auto_ptr(T* ptr) : _ptr(ptr) {}

	// 拷贝构造, 控制权转移
	auto_ptr(auto_ptr<T>& ap) : _ptr(ap._ptr) { ap._ptr = nullptr; }

	// 赋值重载, 控制权转移
	auto_ptr<T>& operator=(auto_ptr<T>& ap) {
		if (this != &ap) { // 避免自己给自己赋值
			if (_ptr != nullptr)
				delete _ptr;
			_ptr = ap._ptr;
			ap._ptr = nullptr;
		}
		return *this;
	}

	T& operator*() { return *_ptr; }

	T* operator->() { return _ptr; }

	~auto_ptr() {
		if (_ptr != nullptr) {
			delete _ptr;
		}
	}

private:
	T* _ptr;
};
```

#### `shared_ptr`模拟实现

```cc
template <class T>
class shared_ptr {
public:
	explicit shared_ptr(T* ptr = nullptr) : _ptr(ptr) {
		if (_ptr == nullptr) {
			_p_count = nullptr;
		} else {
			_p_count = new int(1);
		}
	}

	shared_ptr(T* ptr, std::function<void(T*)> del) : _ptr(ptr), _del(del) {
		if (_ptr == nullptr) {
			_p_count = nullptr;
		} else {
			_p_count = new int(1);
		}
	}

	T& operator*() { return *_ptr; }

	T* operator->() { return _ptr; }

	~shared_ptr() { release(); }

	// 拷贝构造
	// shared_ptr的拷贝构造要共享对象, 同时增加引用计数
	shared_ptr(const shared_ptr<T>& ap)
		: _ptr(ap._ptr), _p_count(ap._p_count), _del(ap._del) {
		if (_p_count != nullptr)
			(*_p_count)++;
	}

	// 引用计数--, 最后一个智能指针负责释放对象
	void release() {
		if (_p_count == nullptr)
			return; // 此时说明该对象已经被移动过了, 资源已经被窃取了
		if (--(*_p_count) == 0) {
			_del(_ptr);
			delete _p_count;
			_ptr = nullptr;
			_p_count = nullptr;
		}
	}

	// 赋值重载
	shared_ptr<T>& operator=(const shared_ptr<T>& ap) {
		if (this == &ap)
			return *this;
		release();
		_ptr = ap._ptr;
		_p_count = ap._p_count;
		_del = ap._del;
		if (_p_count != nullptr)
			(*_p_count)++;
		return *this;
	}

	// 移动构造
	shared_ptr(shared_ptr<T>&& up)
		: _ptr(up._ptr), _p_count(up._p_count), _del(up._del) {
		up._ptr = nullptr;
		up._p_count = nullptr;
	}

	// 移动赋值
	shared_ptr<T>& operator=(shared_ptr<T>&& up) {
		if (_ptr != nullptr)
			release();
		_p_count = up._p_count;
		_del = up._del;
		_ptr = up._ptr;
		up._ptr = nullptr;
		up._p_count = nullptr;
		return *this;
	}
    
    int use_count(){
        return *_p_count;
    }

private:
	T* _ptr;
	int* _p_count;
	std::function<void(T*)> _del = [](T* ptr) { delete ptr; };
};
```

### `Shared_ptr`和`weak_ptr`

#### shared_ptr循环引用问题

- shared_ptr大多数情况下管理资源非常合适，支持RAII，也支持拷贝。但是在循环引用的场景下会导致资源没得到释放内存泄漏，所以我们要认识循环引用的场景和资源没释放的原因，并且学会使用weak_ptr解决这种问题。
- 如下图所述场景，n1和n2析构后，管理两个节点的引用计数减到1
1. 右边的节点什么时候释放呢，左边节点中的`_next`管着呢，`_next`析构后，右边的节点就释放了。
2. `_next`什么时候析构呢，`_next`是左边节点的的成员，左边节点释放，`_next`就析构了。
3. 左边节点什么时候释放呢，左边节点由右边节点中的`_prev`管着呢，`_prev`析构后，左边的节点就释放了。
4. `_prev`什么时候析构呢，`_prev`是右边节点的成员，右边节点释放，`_prev`就析构了。
- 至此逻辑上成功形成回旋镖似的循环引用，谁都不会释放就形成了循环引用，导致内存泄漏
- 把`ListNode`结构体中的`_next`和`_prev`改成`weak_ptr`，`weak_ptr`绑定到`shared_ptr`时不会增加它的引用计数，`_next`和`_prev`不参与资源释放管理逻辑，就成功打破了循环引用，解决了这里的问题

#### weak_ptr

- weak_ptr不支持RAII，也不支持访问资源，所以我们看文档发现weak_ptr构造时不支持绑定到资源，只支持绑定到shared_ptr，绑定到shared_ptr时，不增加shared_ptr的引用计数，那么就可以解决上述的循环引用问题。
- weak_ptr也没有重载operator*和operator->等，因为他不参与资源管理，那么如果他绑定的shared_ptr已经释放了资源，那么他去访问资源就是很危险的。weak_ptr支持expired检查指向的资源是否过期，use_count也可获取shared_ptr的引用计数，weak_ptr想访问资源时，可以调用lock返回一个管理资源的shared_ptr，如果资源已经被释放，返回的shared_ptr是一个空对象，如果资源没有释放，则通过返回的shared_ptr访问资源是安全的。

```cc
int main() {
	std::shared_ptr<string> sp1(new string("111111"));
	std::shared_ptr<string> sp2(sp1);
	std::weak_ptr<string> wp = sp1;
	cout << wp.expired() << endl;
	cout << wp.use_count() << endl;
    
	// sp1和sp2都指向了其他资源，则weak_ptr就过期了
	sp1 = make_shared<string>("222222");
	cout << wp.expired() << endl;
	cout << wp.use_count() << endl;
    
	sp2 = make_shared<string>("333333");
	cout << wp.expired() << endl;
	cout << wp.use_count() << endl;
    
	wp = sp1;
	// std::shared_ptr<string> sp3 = wp.lock();
	auto sp3 = wp.lock();
	cout << wp.expired() << endl;
	cout << wp.use_count() << endl;
    
	*sp3 += "###";
	cout << *sp1 << endl;
    
	return 0;
}
```

```cc
// 需要注意的是我们这里实现的shared_ptr和weak_ptr都是以最简洁的方式实现的，
// 只能满足基本的功能，这里的weak_ptr lock等功能是无法实现的，想要实现就要
// 把shared_ptr和weak_ptr一起改了，把引用计数拿出来放到一个单独类型，shared_ptr
// 和weak_ptr都要存储指向这个类的对象才能实现，有兴趣可以去翻翻源代码
template <class T>
class weak_ptr {
public:
	weak_ptr() {}
	weak_ptr(const shared_ptr<T>& sp) : _ptr(sp.get()) {}
	weak_ptr<T>& operator=(const shared_ptr<T>& sp) {
		_ptr = sp.get();
		return *this;
	}

private:
	T* _ptr = nullptr;
};
```

#### shared_ptr的线程安全问题

- shared_ptr的引用计数对象在堆上，如果多个shared_ptr对象在多个线程中，进行shared_ptr的拷贝构造时会访问修改引用计数，就会存在线程安全问题，所以shared_ptr引用计数是需要加锁或者原子操作保证线程安全的。
- shared_ptr指向的对象也是有线程安全的问题的，但是这个对象的线程安全问题不归shared_ptr管，它也管不了，应该有外层使用shared_ptr的人进行线程安全的控制。
- 下面的程序会崩溃或者A资源没释放，bit::shared_ptr引用计数从int*改成atomic<int>*就可以保证引用计数的线程安全问题，或者使用互斥锁加锁也可以。

```cc
struct AA {
	int _a1 = 0;
	int _a2 = 0;
	~AA() { cout << "~AA()" << endl; }
};
int main() {
	bit::shared_ptr<AA> p(new AA);
	const size_t n = 100000;
	mutex mtx;
	auto func = [&]() {
		for (size_t i = 0; i < n; ++i) {
			// 这里智能指针拷贝会++计数
			bit::shared_ptr<AA> copy(p);
			{
				unique_lock<mutex> lk(mtx);
				copy->_a1++;
				copy->_a2++;
			}
		}
	};
	thread t1(func);
	thread t2(func);
	t1.join();
	t2.join();
	cout << p->_a1 << endl;
	cout << p->_a2 << endl;
	cout << p.use_count() << endl;
	return 0;
}
```
